# 两端 App UI 改版独立验收清单

本次范围：乘客端采用简洁、成熟的网约车界面；司机端面向年长出租司机，突出大字、大按钮、高对比和明确下一步。此文档是源码基线检查及候选验收计划，不代表新版界面已经通过测试。

独立审查只读两端源码，不修改两主对话负责的实现，不发布 APK 或云服务。后台 UI 本轮保持不变。候选完成后须记录源码版本、APK SHA256、安装包版本、设备型号/分辨率、系统字体倍率、证据截图和实际结果。

## 跨两端的必测组合

- 默认字体、1.3 倍字体、1.5 倍字体；司机再各组合应用大字开关。先记录系统原设置，测试后恢复。未经协调不改正在联调用的模拟器设置。
- 约 360dp 宽的小屏与当前联调用模拟器尺寸；竖屏为主。采用真实系统字体缩放，不用截图缩放代替。
- 显示系统导航栏、键盘展开、错误条出现时，底部动作不遮挡。使用至少一条长中文地址、长取消原因/投诉、较长金额及报价版本。
- 弱网/服务暂停后旧数据应说明未更新；错误可读且有重试；不能报成功后实际未提交。输入内容及原有幂等请求策略不得因页面重排丢失。
- 辅助阅读重点检查图标按钮有可理解语义名称、焦点顺序合理、状态不是仅颜色。截图能看到按钮不等于其语义或触控范围可用。
- UI 改版不得更改身份、订单编号、金额分单位、配对/支付版本校验、退款累计口径、权限与业务状态限制。候选独立代码检查重点看 action/payload/enabled/状态分支是否因布局调整改变。

## 有意义的验证方式与通过条件

第一阶段：独立检查候选差异，定位共享主题/按钮/输入组件以及订单状态分支；确认无新增硬编码凭据、业务旁路或假状态。字号、固定高度、色值搜索只作为检查线索，不把搜索结果数量包装为通过率。

第二阶段：两主对话分别准备 APK 与测试账号/订单，独立检查者使用约定模拟器实际操作。必要截图必须来自候选 APK，不使用设计图代替。不得在两主对话同时操作的模拟器上抢占输入。

第三阶段：同一订单用两端改版候选走通主要阶段，后台核对编号、状态与金额。视觉回归和业务回归分别记录；一项通过不能代替另一项。

最终以“在指定设备、字体倍率和业务状态下实际可读、可操作且真实业务状态一致”作为通过依据。没有模拟器/账号/状态资源的项目标为未执行并说明条件，不标通过。
