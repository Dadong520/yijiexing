# 宜捷行长期自主交付约定

模式：反馈驱动；唯一协调者沿用中央 SESSION_REGISTRY 的 coordinator。用户在原 ChatGPT 协调会话提交体验反馈，不管理子任务、开发会话、合并、测试与体验发布。

## 1. 接入边界

本约定补充已有 AGENTS、START_HERE、MEMORY_POLICY 与 DECISIONS；用户最新决定优先。保留中央目录、已发布成果、现有角色与模型选择，不建立第二协调者，不重写业务规则，不重做已经发布的版本。

本模式由原会话收到反馈触发，每轮持续推进到体验发布及回读，或者遇到确实无法自行解决的阻塞。空闲时等待反馈，不无变化轮询模型。不是额外的常驻服务；电脑睡眠、应用停止、网络或配额异常可能中断，恢复时从短交接继续，不能承诺关机后运行。

## 2. 用户只提供体验反馈

用户可以直接说“这里不好用”“这个页面需要调整”，附截图和期望即可，不要求先写技术需求或任务卡。协调者把反馈转成有编号的需求、验收条件和优先级，关联正在体验的版本。

常规实现细节、模块拆分、技术方案、派单顺序和兼容修复由协调者决定并记录。不把内部问题逐个转回给用户。不要求用户向开发会话转发消息、检查提交号或执行发布命令。

有歧义时先依据既有决定和界面行为判断；只有会明显改变用户意图、真实业务规则或既有授权边界且无法合理推断的关键问题，才合并成一条简短问题。外部凭据或服务缺失时准确标记阻塞，其他独立工作继续。

## 3. 每轮必须完成的闭环

1. 恢复中央状态与实际基线；运行现有角色自检，不复制别人的会话 ID。
2. 整理反馈和已批准待办，选择一个可交付批次；创建任务、唯一文件归属、分支、依赖及部署负责人。
3. 按既有分工调用独立 Codex 角色和 Gemini/反重力；落实实现、自测和提交。仅在边界明确时并行，保留共享后端唯一目录。
4. 组织非作者独立验收；失败由协调者直接派回修复并复验，不把“代码生成”当完成，不把不可用测试当 PASS。
5. 协调者集成，提交联调修复，对最终准确 SHA 完成适用测试与发布门禁。
6. 按既有授权自主发布独立体验项目，无需逐轮询问“是否开始”“是否合并”“是否发布”。只发布已验收的批次。
7. 回读实际服务、版本与产物；保存部署回执及数据兼容证据，更新任务板、STATE、短交接和源码检查点。
8. 向用户交付体验地址、版本、变化、建议验证点与已知限制。到这里才将该批次标记为待用户体验。

若任务超出单轮上下文，应先保存可核验交接并按现有换会话规则接续，不能只给计划后把后续调度交回用户。自动换会话能力未实测时明确说明，不承诺无限自治。

## 4. 验收与发布边界

继续使用现有 check_coordination.py 的角色及准确 SHA 发布检查。作者不能验收自己；任务 releaseReady、验收 PASS、测试、证据及部署负责人必须符合现有门禁。结构检查通过不等于业务通过。

仅独立体验项目 yijiexing-driver-demo-1023/us-west1。保留既有账号、会话、数据、接口、IAM/IAP边界、Android签名，以及 Cloud Run automatic/min0/max1/请求计费；不保活、不自动暂停，不接触原测试或生产环境。

未接地图、微信、真实支付等能力继续逐项标明，不能暗中猜测规则、用模拟冒充真实接入或借本约定申请额外消费服务。依赖当前已有账号、工具和权限；权限受限时向协调者汇总，不使用跳过权限参数。

## 5. 失败恢复与节奏

超时或流中断后，先确认命令、后台任务、提交及发布是否已经执行，禁止盲目重跑。保留未提交工作和原日志，按具体任务精确恢复上下文。

连续两轮同类修复失败时，协调者先缩小问题、换执行策略或安排独立诊断，不无上限重试。同一文件和同一部署环境只允许一个写入者或发布者。每阶段、等待或退出前按现有字节预算保存短卡。

## 6. 给用户的版本回执

每次发布只需提供：

- 体验入口与版本：真实可访问地址及准确版本。
- 本轮完成：用户可感知的变化，关联反馈编号。
- 建议验证：3–5 个可直接操作的场景。
- 自动检查：实际通过项、未通过项和 NOT_RUN。
- 已知限制：需要用户知道的影响，不隐瞒模拟或未接服务。
- 后续状态：等待本轮体验反馈；已批准但未完成的待办仍由协调者维护。

不把内部派单、Git操作和常规测试操作变成用户作业。下一轮从用户自然语言反馈继续。
