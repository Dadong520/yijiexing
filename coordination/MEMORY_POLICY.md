# 项目记忆、上下文预警与换会话协议

协议版本：2026-10-26-v3。适用于coordinator、backend、frontend和Gemini/反重力。用户最新明确要求优先。目的：用短而可核验的资料接续长期项目，减少翻历史与重复调查。

## 1. 哪种信息保存在哪里

| 层 | 文件 | 写入时机与责任 |
|---|---|---|
| 稳定约束 | AGENTS.md、DECISIONS.md、contracts | 用户决定/接口变化当轮记录；协调者维护索引，业务负责人审查 |
| 当前状态 | STATE.md≤8KB、BOARD.json、SESSION_REGISTRY.json≤6KB | 完成阶段、发布/合并、等待、交接、结束；协调者唯一写入 |
| 工作细节 | tasks/<id>.json≤8KB、handoffs/<role>.md≤6KB | 负责人每阶段及约40分钟有效工作更新；建议卡片2–4KB |
| 原始依据 | evidence/<id>/、Git SHA/PR/发布回执 | 实际命令、退出码、截图、失败原因、精确源码及产物绑定 |
| 历史 | archive/<date>/ | 完成任务归档，不把全部旧材料塞回当前卡 |

README只写当前入口、实际版本和能力边界，不能保留旧“已停云/未发布”冒充当前事实。代码/版本历史以Git和固定SHA为准；已授权用户的新决定以其指令为准；部署和测试以实际回执为准。发生冲突先定向复核最新权威依据，不能仅以文件修改时间或旧聊天猜测决定。

## 2. 中央状态与工作树的分工

本机中央目录：`/Users/dongge/Documents/New project 2/coordination`。只有coordinator更新STATE、BOARD、SESSION_REGISTRY和DECISIONS，各角色只更新自己的中央handoff与任务指定文件。不同角色不并发改同一JSON。
工作树的coordination是可提交快照，不能用旧副本覆盖中央。提交时从中央**选择本任务文件**同步，检查基线/检查点/文件归属，不整目录覆盖。另一设备无此中央目录时，明确指定本机控制目录，从Git main已提交检查点恢复，再核对真实部署；缺失的未提交改动标UNKNOWN，不能假装已恢复。

## 3. 检查点包含什么

角色短卡至少写：协议版本、角色与会话ID、任务ID、更新时间、sourceRoot/branch/完整HEAD、未提交文件及归属、已完成/未完成、长期决定引用、实际测试与证据、已知失败与NOT_RUN、资源所有权、下一项具体动作、待合并SHA及是否已经发布。
完成一个阶段、约40分钟有效工作、等待/结束、合并/发布前后、看到自动压缩提示时立即更新；40分钟是项目检查节奏，不是模型技术上限。新决定不能等到第40分钟才记。交接时先保存，再发简短通知，卡片记录是入口，历史聊天不是启动必读。

## 4. 预警信号与动作

上下文百分比只有产品/工具可靠给出时才记录，并注明来源/时间；本项目目前无法统一获得三个桌面会话与Gemini的精确上下文用量，统一留null/UNKNOWN。账号额度、对话条数、运行时长不能冒充上下文占用。

- NORMAL：最近检查点准确，能明确基线/下一步。只读任务有关资料继续。
- CHECKPOINT_REQUIRED：出现一次可见压缩提示、重复调查、记错决定、恢复资料明显变大，立即补卡，按START_HERE恢复，给协调者一句风险提示。
- HANDOFF_RECOMMENDED：短时间反复压缩并增加恢复成本；同一阶段第二次记错/重复调查；或准备在已很长的会话开启下一项大任务。先向用户说明原因、已保存路径及推荐切换点，本阶段不扩范围。若平台可靠显示占用≥70%，也按本档处理。
- HANDOFF_REQUIRED：无法可靠分清当前源码/已发布版本、已确认决定反复冲突，或预警后仍发生关键记忆混乱。停止新增写入/新派单，先按权威证据消除冲突并保存短卡；交接新会话后再继续。可靠占用≥85%时采用这一项目预防门槛。

70%/85%、40分钟及事件规则均为本项目保守约定，不是OpenAI官方限制，也不能保证平台每次压缩前都能通知。单次压缩不强制换对话；只统计实际可见事件，不推测压缩次数。无遥测时依靠可见信号，不能报假精度。每角色自行汇报，coordinator记录；空闲不反复轮询、不调用模型来“测记忆”。

预警通知模板：“建议在<阶段>后换新<角色>对话。原因：<实际信号>。已保存<路径/检查点>。接手从<入口>开始；旧对话不再接新大任务。”

## 5. 怎么切换与避免双重指挥

先补卡/保存未提交清单与资源归属，结束或明确交接正在运行的CLI、ADB、Chrome和部署；原样保留未提交成果，不为换会话强行重置/清理。写清是否存在不允许中断的发布，不能在两会话同时合并/部署。
用户自行新开并粘贴NEW_CHAT_PROMPT，或明确要求创建新对话后再创建。普通“完善记忆方案”不代表授权自动替用户新建/关闭会话。新coordinator按启动顺序核对，确认用户明确接任后，把旧ID移入retiredCoordinatorThreadIds，登记唯一新coordinator/发布负责人，再通知两个角色新的协调ID。旧coordinator只交接，不继续派新任务。角色自检必须传本会话真实ID，不能抄用登记中的新ID冒充接任者；无法确认真实ID就先核对，不继续写。新backend/frontend同样替换角色ID，由协调者统一登记；用户无需维护多个群聊。
不要一次复制整段旧聊天到新会话。恢复时优先读短卡；只有发现一个具体缺口，才打开一个原始证据/旧任务。任务完成后的历史恢复默认不读。

## 6. Gemini和节省额度

保持用户选定模型与已验证入口，以GEMINI_CLI.md为准，不假定PATH里的同名程序就是当前应用。每任务新执行上下文，只给规则入口、任务ID、基线、允许文件、验收、时限；续跑必须使用该任务精确conversation_id。阶段输出短结论+SHA+证据路径+未通过项，长日志存文件。
主要实现、常规修复和自测优先Gemini；Codex处理协调、关键规则、疑难与独立验收。只唤醒本任务负责人；复用精确SHA且字节相同的测试，不各角色重复全套。作者不验收自己；换对话不重新跑已经有效的完整测试，只补差量/缺口。

## 7. 检查器和边界

提交前运行check_coordination.py，活动角色接单/恢复用`--memory-role <role> --session-id <真实会话ID>`。检查文件预算、注册表/ACK/角色映射和声明的预警状态；这不会读取模型内部上下文、不会自动监控桌面、不能证明模型没有遗忘，也不是任何拥有权限的人都无法绕过的技术锁。
规则已提交Git并通过角色ACK才算本轮固化；未来每次派单附中央入口与协议版本。工作回合结束后不自行常驻，除非用户另有明确自动化授权。
