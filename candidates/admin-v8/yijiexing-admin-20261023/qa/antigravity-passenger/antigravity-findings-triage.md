# 反重力静态发现独立复核与分级

日期：2026-10-23。复核对象：`qa/antigravity-static-review.md`（反重力静态初稿）。本次只读 Android、共享后端、测试代码及已有日志；没有操作模拟器、连接云服务或改动实现。以下判断不冒充设备复现结果。Android 与线下议价仍在更新，源码修复和最终 APK 应分别验收。

## 分级结论

| 反重力发现 | 独立判定 | 处理 |
|---|---|---|
| 1. 任意 4xx 清除 pending 导致幂等失效 | **必须修复，按 P1 跟踪，但原报告 400/409 推导不准确**。单次普通 400/409 不会把已提交付款伪装成失败；真实问题是先发生不确定提交，再遇鉴权 401/403 清掉旧键 | 已通知 Android：错误不清未决键，成功才清；按稳定 passenger.id 隔离，状态尚未取得身份时禁止动作，禁止用会变化的 token 做签名 |
| 2. 超时缺自动对齐和状态锁定 | **原重复提交风险推断不成立；降为运行验证/体验建议**。相同 payload 重试复用持久化 requestId，后端去重；前台已有自动同步和失败退避 | 不建议简单强制永久锁按钮。实测丢响应、重启与同账号重登后重试，仅产生一次副作用；先完成第 1 项修复 |
| 3. 单张上传无法覆盖最多三张 | **不是当前实现缺陷**。最多三张指总量，不要求一次多选；后端追加，UI 支持继续上传至三张 | 保留设备连续选择两张及第三张后入口收起的验收用例，不需为此重写上传协议 |

## 1. 4xx、回滚与不确定提交的实际边界

后端证据：

- `cloud-service/server.py:69` 执行乘客 action 后取得返回状态；只有正常完成才在第 151 行提交，异常在第 153 行回滚，再转换为错误响应。乘客 action 没有管理登录失败计数那种显式提交错误状态的例外。
- `cloud-service/passenger.py:156` 先查 `(passenger, request_id)` 已成功记录；相同 hash 直接返回旧结果，payload 不同才返回 409。记录结果与动作修改在同一事务中。
- `cloud-service/cloud_server.py:167` 先暂存响应，不直接发送。第 222—224 行重新读取权威快照、执行业务、完成 CAS；第 225—238 行把写失败、冲突或结果不确定统一改为 503 并丢弃本地副本。4xx 响应不能被当作“这次 CAS 写入已成功但仍返回普通业务错误”。
- `cloud-service/snapshot.py` 的上传失败明确允许“远端可能已经提交”，因此不确定结果是 503，下一请求重读权威快照。
- `tests/test_passenger.py:113` 已有不确定创建结果返回 503 后沿用 requestId 重试只保留一单的用例。既有 `qa/backend-full-with-negotiation-regression.log` 记录 130 项通过，本次未重新运行该套测试。

所以，原报告以“制造一次 400/409 后 UUID 改变”直接推断重复扣款，证据不足。当前支付另有 `paid` 与 `credited` 守卫；发票申请、评价和订单投诉也各有业务约束。不能把所有动作都说成会重复收费。

仍然成立的真实重试链：

1. 同账号提交 `feedback.submit` 或不带 id 的 `favorite.save`，使用请求键 K1。
2. 云端已经持久化，但客户端收到 503 或发生网络超时，K1 保留。
3. 用户下一次重试时，会话已失效返回 401，或访问码错误返回 403。此类错误发生在业务 action 的成功记录查询前，不能证明 K1 没有成功。
4. 原 Android `catch (ApiError)` 对所有 4xx 清掉 K1。
5. 同账号恢复登录后重试相同内容，生成 K2，后端按新意图再次追加反馈/地址。故必须保留仍未确认的历史请求身份。

最小修复已直接交给 Android agent：

- 最简单安全规则是仅在明确成功后清 pending，错误继续保留；当前后端不缓存失败响应，校验失败后同键重试不会锁死。
- 若选择按错误类型处理，至少必须保留 401/403/408/429、访问门禁错误和无法确认业务错误来源的响应，不能把它们当作此前不确定请求未生效的证明。
- 同账号重登保留待决历史，跨账号使用不同稳定乘客 id 做签名。现有 logout 不清 pending 是正确基础；`state.passenger.id` 未取得时应先刷新并禁止动作，避免 token 变化导致签名变化。
- 验收应比较实际副作用数量，不只比较界面文案或 UUID 是否相等：丢响应→鉴权失败→重登→重试，反馈/地址只新增一次，其他账号互不复用请求。

## 2. 超时后的同步与幂等

`MainActivity.kt:69` 使用生命周期 STARTED 范围中的每 5 秒循环调用 `refresh(true)`；`PassengerStore.run` 对网络异常设置退避，`refresh` 在退避期后继续同步，并非完全没有自动对齐。网络超时不清 pending；同 payload 仍用原 requestId，后端先返回旧结果。

用户修改 payload 是新的业务意图，应重新校验；不宜为了掩盖状态不确定而永久禁用全 App。可改善错误后引导刷新，但这是体验选择，不是报告已证明的重复提交漏洞。本项与第 1 项的鉴权重试链联合验证即可。

## 3. 投诉图片总量

`cloud-service/order_options.py:121` 读取已有附件，第 122 行校验 `已有数量 + 新增数量 <= 3`，第 133 行使用 `existing + added` 追加。不会单张覆盖旧附件。

Android `OrderDetail.kt` 对已有附件逐张展示；少于三张时显示“从相册添加投诉图片 (n/3)”按钮。单次选择一张与总量三张兼容。`tests/test_passenger_options.py:61` 已覆盖归属、非法媒体无部分残留、已存在附件时总量拒绝；该测试未代替相册连续选择操作的设备验收。
