## LA-001：司机占用集合混入乘客未结账状态

源码：`cloud-service/passenger.py:268` 对共享 `order.accept/order.bid` 扫描任一 WAIT_PAY 并报409；`:181` 在乘客 `order.selectDriver` 时也把 WAIT_PAY 列为司机进行中。相对地，`domain.py:23` 的 ACTIVE 为 BID_SENT/PREPAY/RESERVED/PICKUP/ARRIVED/TRIP，本来不含 WAIT_PAY，`:93–109` 的统一 `new_accept` 已按该集合校验。

触发：司机完成乘客 A 的标准行程至 WAIT_PAY；乘客 B 创建新标准/预约/BID；司机接单或报价会被第一处拒绝。即使只删除第一处，BID 选中司机仍可能被第二处拒绝。NEG 发起当前使用 ACTIVE，不存在同一 WAIT_PAY 拒绝，造成入口规则不一致。

实际证据补充：根任务于01:23:13只读后台记录 [logic-audit-before-fix.json](../qa/logic-audit-before-fix.json)，司机0001在线，私有合成单 `YC1001` 为 WAIT_PAY、2850分、paid=false、credited=false，创建于前一天；共享订单列表无WAIT_PAY。`sync_shared_orders` 将visible+private合并（`:116`），`:268`扫描两者，因此该私有旧单足以触发共享接单拒绝。此为用户反馈、云只读快照和可达源码的相互印证；根未为此操作0001新业务，本子任务也未操作001。不能因为后台canonical订单没有待付款就排除问题。

建议：统一“司机实际占用”判断并同时修共享接单、报价、选中检查；乘客 `UNFINISHED`（`passenger.py:19`）及创建限制（`:128`）、NEG认领限制（`negotiation.py:66`）保留 WAIT_PAY。Android 首页主订单选择也要区分未结账旧单与新在途单。

必须回归：旧单 WAIT_PAY→新标准接单；新 BID 报价/选中；旧单晚付发生于新单 PICKUP/TRIP；旧单重复付款和支付失败；新单不被推进或覆盖；余额只加旧单金额；乘客 A 仍不得新叫单。另验证真正的 PREPAY/PICKUP/ARRIVED/TRIP 仍拒绝第二个占用订单。

## LA-002：司机 API 投影带出乘客私人投诉

源码：`passenger.py:102–115` 从 canonical 订单 clone，仅删除 passengerId/bids，未删除 complaints、附件元数据、回复或管理员处理字段。`admin_console.py:169–172` 将处理回复写回 canonical 后同步司机投影。已有 `yijiexing-passenger-20261023/qa/ui-redesign-regression/standard-passenger-complaint-state.json` 的 driver.complaints 包含乘客投诉正文，证明此前联调导出的司机结果存在该字段。

触发：乘客在共享完成单提交投诉，后台回复；原接单司机读取 `/api/state`，可获得 complaints 数据，即使司机 App 没有显示它。影响是数据隔离而非单纯界面问题。附件二进制另由乘客身份/归属检查（`order_options.py:36–42`）保护，不能据元数据外泄进一步宣称图片下载已可越权。

建议：建立司机订单白名单投影，移除乘客私人投诉/附件/回复和无必要管理员字段；司机自己的投诉仍从司机 profile 返回。避免仅修改 Android 隐藏。回归需分别断言乘客本人、后台授权角色、司机状态及附件读取范围，历史数据不删除。

## LA-003：普通订单付款与后台调价之间缺少确认金额约束

源码：`passenger.py:186–195` 付款只调用 `validate_negotiation_payment`；该函数 `negotiation.py:93` 对非 NEGOTIATED 直接返回。后台 `admin_console.py:148–149` 可改变 WAIT_PAY 的 fare；付款成功及 `domain.py:112` 入账使用请求到达时的 fare。

触发：乘客打开标准单 ¥29.26 的付款确认；管理员将 WAIT_PAY 调整为 ¥40；乘客提交原页面 SUCCESS。即使请求携带旧 amount，非 NEG 服务端不核验，可能以 ¥40 标 paid 并入账。CAS 保证事务不会互相覆盖，却不能证明用户确认了新金额。

建议：对所有支付要求已确认 amount 与价格版本（或安全的订单修订号），变更则409并刷新重新确认；后台调价递增版本。兼容旧客户端时须明确旧客户端被要求升级或采用等价的服务端确认凭证，不能直接强制新字段后破坏现存支付接口。重复成功支付仍应按原 requestId 返回稳定结果，不重复入账。

## LA-004：资质门禁在 NEG 与普通接单不一致

源码：标准/预约/BID `new_accept` 在 `domain.py:109` 要求 certificationStatus=APPROVED；NEG 发起 `domain.py:231–245` 仅核权益、上线和占用状态，没有资质检查。`driver.online`（`:190–196`）也不核资质。配对 `negotiation.py:67–81` 核订单状态、双方屏蔽，但不补资质或当前上线/权益校验。

触发：有 NEG 权益的司机提交资质进入 PENDING（`domain.py:269–284`），仍保持/可打开 online 后发起 NEG 并配对；或发出有效码后其资质被退回，乘客五分钟内继续认领。普通新接单会被拒绝，而 NEG 缺同等守卫。

此外 APPROVED 证件随时间过期后，`new_accept` 只核总状态，不核 validUntil；资质提交时校验日期（`:274–281`）不等于后续每日有效期守卫。

建议：抽取司机新增业务资格校验（资质状态与有效期、必要城市/权益、占用）并用于普通接单、BID选中、NEG创建/认领的适当时点。不能拿普通 new_accept 的 AVAILABLE 检查直接套到 PREPAY 配对。历史行程继续推进和晚付款应不受“禁止新增业务”门禁影响。已配对后资质失效如何处理在途订单需明确业务规则，不能擅自自动取消退款。

## LA-005：司机敏感写操作缺强制幂等键

源码：`domain.py:172` 只在 request_id 非 None 时验证；`:182–185`、`:321` 也是可选幂等记录。`server.py:115` 直接传可为空的 requestId，`cloud_server.py:42–45` 没有补强制限制。`wallet.withdraw`（`domain.py:253–257`）每次新建提现记录并扣可用余额，投诉（共享 `passenger.py:295–301` / 私有 `domain.py:292–295`）每次新建记录。

触发：无 requestId 的提现/投诉已持久化但响应丢失，客户端重发同载荷；额度允许时又生成一笔。5次/日提现上限不是幂等保证。相同非空 requestId 的现有校验可防重，不应把它误报为已失效。

建议：与司机负责人协调，敏感写入强制稳定 requestId，客户端未收到明确结果时保留键；必要时分阶段启用兼容告警。对订单推进尤其要确认重试复用同键，否则一个“下一步”请求若换键可从 PICKUP推进ARRIVED，再推进TRIP（后者仍有尾号保护）。不能仅在按钮点击时生成新 UUID 而不保存未决状态。

## LA-006：后台同状态调价可覆盖另一管理员的结果

源码：`admin_console.py:141` 仅核 expectedStage；`:149` 调整金额不会改变 WAIT_PAY。两名 FINANCE/SUPER_ADMIN 同时基于旧金额操作，后提交者仍满足 stage 检查，覆盖先提交的价格，虽有审计但没有冲突提示。

建议：调价/人工干预提交 expectedVersion 或 expectedFare+可靠修订号；成功后递增版本，旧页面409。不同 requestId 的正常操作不会被幂等表挡住，CAS 串行持久化也不能替代用户视图的乐观并发控制。联同 LA-003 测试付款与调价两种先后顺序。

## LA-007：四位手机尾号不适合作为黑名单主键

源码：`domain.py:285–287` 仅保存 phoneTail；`:108` 接单按尾号拒绝；`passenger.py:299–300` 投诉加入黑名单也用尾号；`negotiation.py:72` 配对时同样使用尾号。

触发：A 与 B 不同乘客有同一尾号，司机屏蔽 A 后 B 也被拒；代叫乘车人更可能与下单账号身份不同。当前合成白名单范围有限不代表模型正确。

建议：共享订单屏蔽使用明确 passengerId 或经确认的 rider 身份，尾号仅展示/上车核验；旧尾号记录迁移时保留为旧演示规则，不凭尾号反向绑定真实账号。屏蔽下单人还是实际乘车人属于待确认业务问题。

## LA-008：“今日”字段实际累计；建议分两层安全修复

证据：`seed.py:22` 初始化 todayIncome=11000、todayAccepted=2、todayCompleted=2；`domain.py:112` 完单付款时只增加，`:206/210/245` 与 `passenger.py:185/275` 只增加接单计数，没有统计日期、跨日清零或按日查询。`domain.py:87` 排名又直接引用todayCompleted。seed初始流水以创建当日时间标记，若直接汇总全部entry会将初始模拟金额误当真实业务收入。`common.py:3–5` 采用UTC+8，应明确日报使用相同时区。

**可立即采用的最小风险修法：** Android 将现有三个字段清楚标为“演示累计收入/接单/完成”，移除“今日”含义，说明含初始模拟数据；保留金额和全部历史数据。此为诚实口径修正，不等于实现日报。后台canonical统计继续保持独立。若本次要求真正按日数据，则不能只在午夜将旧字段和钱包一起清零。

**真正日报的建议方案：** 新增只读 `dailyStats`，返回 date、timezone、income/accepted/completed、口径和数据起点，不复用钱包balance或trial_completed。推荐明确“今日入账收入”“今日接单次数”“今日行程结束次数”，分别按入账事件、接单/选中/认领事件、TRIP结束事件计算，WAIT_PAY也可计完成行程。若要把完成定义为已付完单，应改显示名称并说明，避免晚付款把昨天行程计作今天完成。

- 新写入的业务事件必须包含可靠 driverId、orderId、发生时刻与唯一事件ID；入账事件本身与钱包变动/幂等记录同事务保存。不能只依据当前order.driverId回推历史接单者，因为继续叫车会重新分配。
- 历史 shared事件可以按已知可靠事件回填；无法准确归属的旧私有seed、缺时间/无actor的旧事件标为不计入或历史覆盖不足，不能猜历史日期。使用明确来源/类型，避免解析“今天09:50”或title当唯一业务类型。
- 钱包、真实订单、退款及原累积值全部保留；只在读取时按UTC+8日期范围聚合，不新增常驻定时服务。旧客户端兼容字段保留，新客户端优先新字段。
- 退款收入口径先定为毛入账、退款及净入账分别展示，避免拿余额（含初始资金/提现）当收入。退款发生日和原收入发生日分别记录，不回写已经发生的历史事件。
- 回归至少覆盖午夜边界、昨天WAIT_PAY今天付款、前日接单今日结束、同单重派、seed排除、重复付款、退款及提现；司机首页与后台不同范围必须可解释。

当前建议优先LA-001与投诉隔离；“今日”可先正确更名以消除误导。真正日报涉及事件完整性，应独立实现测试，不把简单清零作为安全修复。

### BID_SENT 的占用是确定行为，是否修改仍需业务确认

`domain.py:23/94` 的ACTIVE包含BID_SENT；共享投影 `passenger.py:106` 将未选中的本人报价转成BID_SENT，因此报价后其它新接单会被阻断。`passenger.py:181` 虽没有BID_SENT，但`:183–184`又调用new_accept，其他待选报价仍可能阻断选中。这是可达的确定逻辑，不是猜测；是否不合理属于**规则待确认（P2产品决策，不直接修）**，用户当前明确豁免的只有WAIT_PAY。

若决定“报价不占用”：不能只从ACTIVE删除BID_SENT；选中时必须原子核对司机实际占用及所选报价仍有效，成功后使该司机其他未选报价失效/撤回并通知乘客刷新；司机接标准单后也须处理其其他报价。两个乘客同时选择同一司机仍只能一单成功。若保留“报价即暂占用”，UI应清楚提示占用/撤回/十分钟超时，不将待选显示为已接单。

## 已核保护与不应误报的事项

- **晚付与新单：** `passenger.py:119–122` 从旧单 driverId 同步当前司机状态，再调用 `credit`；`domain.py:111` 的 credited 防重复及 `passenger.py:189` 的 paid 快速返回已有保护。源码未看到直接用旧全量 state 覆盖新单的支付代码；仍必须用两个订单做时序回归，不能仅凭静态阅读宣布安全通过。
- **并发与持久化：** `server.py:55/151–153` 的服务锁、提交/回滚与 `cloud_server.py:220–241` 请求锁及 CAS失败503，`snapshot.py:158–169` 持久化后再放行响应，避免把本地提交直接当云成功。保留同一requestId跨503重试。未执行本次网络故障注入。
- **未中选司机取消：** 虽然 `passenger.py:277` 的授权 OR 条件较宽，但 `:104` 不投影已分配给别人的订单，`:265` 先找投影会404。常规可达链被挡住，不能报告“可取消别人订单”漏洞。建议仍显式区分撤报价与已分配取消作纵深保护。
- **云重置：** `domain.py:308–315` 有 local.reset，但 `cloud_server.py:43` 已禁止，不能报成公开云可清空数据。
- **退款：** PREPAY/接驾取消只在 paid=true 时生成本轮退款；继续叫车把本轮退款移到 refundHistory（`passenger.py:222–225`）；后台费用统计累计两者（`admin_console.py:104–113`）。完成单退款需DONE/paid/无当前退款且余额充足（`:151–155`）；提现审核只处理PENDING（`admin.py:260`），重复审核被拒。不能据没有完整云UI覆盖就称实现缺失。
- **权限：** 管理操作先 permit 再幂等重放（`admin_console.py:122–126`），改角色/停用删除会话（`:185–186`），导出同时核export及dataset.read（`:202–203`）。此次未发现伪造actor提升权限的源码路径。

## 不明确业务规则，先列问题不擅自改变

1. **会员区域暂停：** `benefits.py:71` 已购在期 sub 可令 canAccept=true，即使当前 systemEnabled=false；存量权益快照保留看起来是既有设计。需要区分“停止售卖/保留权益”和“城市紧急停止所有新增订单”，不直接认定已购权益保留为bug。
2. **等待报价是否占司机：** ACTIVE含BID_SENT，意味着司机报价后直到撤回/超时前不能再接其他单。用户此次只明确WAIT_PAY，是否允许多个报价待选、未来预约并行须另确认，不能随手移除全部等待态。
